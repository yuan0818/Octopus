# 仓库背景分析编排

入口为父级「背景知识」，包含「背景查询」（`/background/query`）和「分析任务历史」（`/background/tasks`），`/background` 默认重定向到查询页，与「业务 API 测试」同级。默认按项目、模块、分支、提交、环境查询保存的背景，展示当前模块规则及仓库其他模块规则（包括网关），避免过滤掉跨模块背景。旧 `/business-testing/repository-analysis` 链接保留范围后重定向。人工配置仍在项目背景页维护。

右侧对话区提供「询问背景」和「调度分析」两个明确操作：询问通过只读模型接口回答，携带当前版本报告、证据索引、人工背景及最近12条对话，不读取全量源码、不启动任务；调度把用户输入保存为分析目标，由既有工作流执行目录规划、按需取证及全模块归纳。任务抽屉展示阶段、计划顺序、依赖、当前动作、已读文件、工具记录、分项记忆和恢复入口。问答会话当前只保留在页面内存，切换查询范围会清空；后台分析任务和目标持久化保存。

服务端维护 system prompt（编排规则、工具边界和证据要求）；用户目标在 PLAN/ANALYZE/SYNTHESIZE 三阶段作为 user context 传入，不能替代系统规则。回答校验源码引用只能来自当前提交。凭据独立存储，不进入模型背景投影。恢复任务保留原目标和检查点，改变目标必须重新规划。

执行流程：

1. COLLECTING：读取所选 Git 提交的文件目录及完整模块清单，不读取工作区未提交文件。
2. PLANNING：向模型提供目录概览和模块列表，由模型输出分析项、目标、顺序与依赖。每个模块必须恰好分配一次。
3. ANALYZING：各分析项通过 LIST 分页查询文件名、READ 指定文件、DONE 保存记忆。源码范围由模型决定，不按固定框架或类名筛选。已完成依赖项的记忆随下一项提供。
4. SYNTHESIZING：将全部分项记忆提供给模型，独立总结职责、跨模块关系、共享约束及未解决问题；此阶段不重新发送原始源码。校验计划项和模块全部覆盖后才标为 READY。

计划、源码证据、每项记忆与进度加密保存于原有 business_repository_analysis 快照。服务中断、模型失败或最终总结失败后，默认从检查点继续；已完成分项不重做。最终总结校验失败会携带具体字段限制自动修正一次，修正仍失败时只重试总结；修正也保留全部分项记忆输入，不持久化无效候选。界面的「重新规划全部分析」会显式重新采集并规划。迟到写入受租约和所有者校验保护。

## 覆盖与限制

- 规划与分项模型调用最多240秒，最终总结最多600秒；场景服务分别留出260秒和620秒响应等待，超时保存检查点。
- 支持最多64个已知模块、32个分析项；超过限制明确失败，不静默丢弃模块。目录最多30000个 Git 普通文件，符号链接和子模块内容不读取。
- 首次模型输入为最多500项的目录概览，标明是否截断；分项可按前缀、文件名和偏移查询全部文件目录，每页150个。
- 每分析项最多12轮取证，耗尽后只允许总结已有证据和缺口，最多两次纠正动作；单次READ最多6个文件，总计最多24份文件及96000字符。重复READ复用缓存；文件预算不足会反馈模型。单项记忆校验失败最多自动修正两次，仍失败保留检查点。分项记忆最多6000字符（模型目标4500字符，为持久化证据引用留出空间）；最终归纳输入超过230000字符会保留检查点并报告预算不足，不截掉前面的记忆。
- 安全读取器当前支持Java源码、Maven依赖及YAML/JSON配置键结构；路由值使用既有安全投影。其他文件格式显示UNSUPPORTED，不发送原文，也不能作为实现规则的证据。源码解析失败、缺少模块索引和截断会明确标注。
- READY表示全部计划记忆已完成总结，并不代表仓库每个文件均被阅读。无有效文件证据的模块以及不支持/截断文件会列为覆盖缺口。部署配置和运行时密钥不属于静态分析证据。

## API

- 场景服务沿用 GET/POST /api/business-testing/repository-analysis，POST 请求可选 restart=true 放弃旧检查点重新规划。
- 查询服务 GET /api/query/repository-exploration 返回指定提交目录，POST /api/query/repository-exploration/read 按精确文件路径读取脱敏证据。
- 源码服务 GET /api/source/tree 返回指定提交的普通文件路径。
- 模型服务 POST /api/business-flow/repository-stage，阶段为PLAN、ANALYZE、SYNTHESIZE。

旧版READY报告仍可读取和用于步骤补全。新任务或显式重新分析使用编排流程；不会自动替换其他版本或环境的报告。

## 模型返回格式与恢复

模型输出先按严格 JSON 语法和当前阶段的字段结构校验。错误区分 EMPTY_RESPONSE、OUTPUT_TOO_LARGE、JSON_SYNTAX、SCHEMA_TYPE、SCHEMA_FIELD，只展示受控的字段路径和预期类型，不保存或展示被拒绝的模型内容、未知字段名或 Gson 原始异常。

规划和分项格式错误最多自动修正两次；最终归纳沿用一次修正预算。格式修正复用同一目录、已读源码和上游记忆，不执行未经校验的动作。模型上下文明示 allowedEvidenceIds 和 evidenceIndex；UNSUPPORTED、空源码及上游记忆中的引用不能冒充当前分项证据。轮次、文件或字符预算耗尽后仅允许 DONE。超过恢复预算后保留检查点与明确诊断，人工继续不会重新读取已保存的文件。

## 分析任务历史

`GET /api/business-testing/repository-analysis/tasks` 按项目、模块、分支、提交、环境、状态和关键字筛选分页摘要。`GET /tasks/{taskId}` 查看指定任务完整快照，`POST /tasks/{taskId}/resume`、`POST /tasks/{taskId}/cancel` 只操作当前任务；任务已被新分析替代时在仓库作用域行锁内拒绝操作。

`business_repository_analysis` 继续保存每个作用域的当前检查点；新增 `business_repository_analysis_history` 按稳定 taskId 保存摘要和完整快照，两者都加密。每次检查点更新与历史写入在同一事务内；新规划归档上一任务，检查点重试沿用同一 taskId。列表只读取摘要，选中详情才读取源码和记忆。升级前尚存的当前快照通过稳定派生 ID 展示，下一次写入或新规划时纳入历史；旧系统已经覆盖的历史无法重建。新增表通过 `db/business-testing.sql` 的幂等建表语句部署。
