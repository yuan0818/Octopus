## 1. 背景与问题

### 1.1 测试模型（已确定的前提）

业务 API 测试按 **单向线性序列** 建模，遵循 Given-When-Then（GWT）：

- **外层（业务流程）严格线性**：执行序列在确认时即完全确定，步骤按固定顺序逐个执行，数据只从前向后传递；不支持分支、条件跳过、跳转、循环或并行。这是保证测试**可靠、确定、可复现**的强制约束（FR-LIN）。
- **内层（单个交易节点）可以复杂**：构造请求（拼装、加密、签名）、解析回应（解密、解包、提取）、字面量断言、数据一致性校验（数据库 / Redis / Kafka）。

### 1.2 设计原则：像 DevOps 工具一样隐藏复杂度

参考 CI 流水线、`docker-compose` 这类工具：使用者描述**想要什么**，工具负责**怎么做**。对 API 测试而言，使用者真正关心、也只有使用者才知道的只有三件事：

| 使用者声明 | 含义 | 例子 |
|---|---|---|
| **调用（call）** | 按什么顺序调用哪些 API | `POST /orders`、`POST /refunds` |
| **验证（expect）** | 每一步要验证什么：回应本身，或数据库 / Redis / 消息等系统中的数据 | “退款单状态为待审核”、“orders 表中该订单状态为 REFUND_PENDING” |
| **依赖（from）** | 后续调用需要前序步骤的哪些上下文 | 退款的 `orderId` 来自创建订单的回应 |

其余全部属于“实现细节”，由平台根据 API 定义、项目背景、仓库背景分析与历史确认结果推导：请求体结构与测试数据、请求参数位置、成功状态码、鉴权方式、加密 / 签名 / 解密、回应包装层、JSON 路径、提取路径、数据层查询计划、执行地址、清理动作、GWT 角色。使用者**不需要手写**这些内容，但**需要能看懂并判断**它们：推导结果以技术形式完整展示，由使用者凭专业判断确认或覆盖。

> **抽象的边界**：隐藏的是“平台内部如何实现”（绑定来源、IR、JMX、预处理工具编号、数据验证计划格式等），不是“HTTP / JSON / 数据库的基础知识”。使用者仍需理解自己在测什么、预期为什么是这个值、推导出的请求和校验是否正确。

### 1.3 现有两种模式与缺口

| 模式 | 局限 |
|---|---|
| 手动编排（画布） | 需要逐字段配置绑定、断言、路径；无法 diff、评审、纳入 git |
| LLM 生成（业务目标 → 规划 → 补全） | 输入是自由文本，人已明确的意图（调用顺序、预期结果、依赖关系）无法“锁住” |

缺少的第三种模式：**用最少的结构化声明锁定意图，其余交给平台**。

## 2. 目标与非目标

### 2.1 目标

- **G1 最小声明**：一个可执行场景的最小写法只需列出 API 路径；加上验证与依赖即是完整测试。每增加一项控制，只需多写一项，不需要先学会底层模型（渐进式披露）。
- **G2 意图锁定**：使用者写出的调用顺序、验证预期、依赖关系、显式给出的值，在转换中**不被 LLM 改变**。
- **G3 上下文驱动**：LLM 推导所需的 API 规格、参数结构和业务语义，来自平台中已有、版本化、可追溯的 API 定义与背景知识，而不是靠猜测或要求使用者手写。
- **G4 同一产物**：三种编写模式都产出同一种 Flow，走同一条确认、执行、回归路径；DSL 与 Flow 可双向转换。
- **G5 测试即代码**：DSL 文件可同步到 git、在 PR 中评审、在 CI 中校验与执行。
- **G6 判定正确**：前置未建立不等于产品缺陷。
- **G7 专业判断留在人**：平台负责“少写”，使用者负责“判对”；任何推导结果都可以被具备基线能力的使用者独立核对，平台不以“降低理解门槛”为代价隐藏技术事实。

### 2.2 非目标

- **NG1** 不支持分支、条件执行、循环、并行、任意脚本（见 FR-LIN）。函数只能以“计算一个值”的方式使用（第 9 节），不能影响执行路径。
- **NG2** DSL 中不出现主机、URL、凭据、数据库连接串、SQL 语句等基础设施细节（覆盖项只能引用逻辑名称）。
- **NG3** 不替代画布与 LLM 规划；三者并存。
- **NG4** 不做负载 / 性能测试语义。
- **NG5** 平台不为了获取上下文而连接被测环境或数据库（与现有“保存背景不建立网络连接”一致）；运行时连接仍只在执行阶段发生。
- **NG6** 不面向无技术背景的使用者设计“零技术知识”编写体验；不以自然语言作为唯一或主要的验证表达方式。

## 3. 术语

| 术语 | 含义 |
|---|---|
| 场景 | 一个 DSL 场景，对应 Flow 中的一个测试点及其执行前缀 |
| 步骤 | 一次 API 调用及其验证，对应 Flow 中的一个交易节点 |
| 声明项 | 使用者在 DSL 中写出的内容：调用、验证、依赖、显式值、可选覆盖项 |
| 推导项 | 平台根据上下文补全的内容；每项带来源与置信度 |
| 锁定 | 声明项在转换中不可被 LLM 改变 |
| API 定义 | 平台对一个 API 版本掌握的全部知识：契约、语义、约束、副作用、数据影响、调用约定（第 6 节） |
| API 知识卡 | API 定义中可由人补充、修订的语义层，叠加在代码推导的事实之上 |
| 上下文包 | 一次 LLM 推导实际收到的、经过裁剪和脱敏的上下文集合，可追溯、可哈希 |

## 4. 使用者与用户故事

### 4.1 能力基线

DSL 的目标编写者具备 **1–3 年相关经验** 的专业技术能力。需求、界面与诊断信息均按此基线设计：不为更低基线简化技术表达，也不要求掌握平台内部实现。

| 假定使用者**具备** | 假定使用者**不需要掌握** |
|---|---|
| HTTP 基础：方法、路径 / 查询 / 请求头 / 请求体、常见状态码及其语义 | 平台 Flow / IR 模型、Binding 来源类型、能力声明 |
| JSON 结构与基本路径表达（`$.a.b[0]`）、数据类型 | JMX、Groovy 模板、JMeter 执行细节 |
| 能阅读 API 契约（OpenAPI 或接口定义），理解必填、枚举、约束 | 请求预处理 / 回应解码工具的编号与参数格式 |
| 鉴权、加密、签名、幂等等概念（知道是什么、何时需要） | 项目中具体的加解密算法实现、网关过滤器代码 |
| 基础 SQL 与所测系统的主要表、缓存键、消息主题的业务含义 | 数据验证计划的内部格式、参数化与上限规则的实现 |
| 测试设计基础：正向 / 负向、前置与清理、同步与异步、幂等与数据隔离 | 租约、批量调度等执行机制 |
| 能判断一个预期值、一次请求、一条数据校验在业务上是否正确 | — |

### 4.2 角色

| 角色 | 典型写法 | 期望 |
|---|---|---|
| 后端开发（DEV） | 路径 + 精确断言 + 显式依赖 | 结果确定、可在 CI 中运行、可评审 diff |
| QA / 测试工程师（QA） | 路径 + 精确断言为主、自然语言验证为辅 + 必要依赖 | 推导准确、可核对；歧义时询问而不是猜 |
| 业务分析 / 产品（评审者） | 不直接编写；阅读 DSL 与报告中的场景名、描述与验证 | 能看懂“测了什么、预期是什么”，在评审中提出业务意见 |

> 业务分析 / 产品如具备 4.1 基线，可以作为编写者；平台不为其提供单独的简化模式。

- **US-01** 作为 QA，我只写三行 `POST /orders`、`POST /orders/{id}/pay`、`POST /refunds` 和退款步骤的断言，平台生成完整可执行的测试草稿（测试数据、依赖映射、鉴权、状态码），我在审阅中看到**实际请求示例、每个依赖的源字段与目标字段、每条断言的 JSON 路径**，逐项核对后确认。
- **US-02** 作为 QA，我写 `db: orders[id=${order.id}].status == "REFUND_PENDING"`，或用自然语言描述后由平台生成；无论哪种，审阅中都显示**等价的只读查询**和所用连接，由我判断是否正确。我不需要知道平台内部的数据验证计划格式。
- **US-03** 作为 DEV，我写 `orderId: ${order.id}` 明确依赖；或只写 `from: [order]`，由平台根据两个 API 的结构匹配字段，我核对映射。
- **US-04** 作为 DEV，我在 PR 中修改 DSL 文件，CI 校验语法、API 路径存在性与依赖合法性，合入后自动运行。
- **US-05** 作为 QA，我在编辑器中输入路径前缀或关键词，看到候选 API 的方法、路径、所属服务与业务说明，选择后填入路径。
- **US-10** 作为业务分析，我在 PR 或平台中阅读场景，能看懂场景名、描述与验证内容并提出意见，不需要理解推导细节。
- **US-06** 作为 QA，当某 API 的定义缺少关键语义（例如字段含义不明、加密方式未知），平台明确告诉我缺什么，并允许我在 API 知识卡中补充一次，以后所有场景复用。
- **US-07** 作为任何使用者，GIVEN 阶段（准备数据）失败时，结果显示“无法判定：前置未建立”，而不是“产品缺陷”。
- **US-08** 作为 QA，加密网关的接口我也只写路径与验证；加解密由平台按仓库背景中的规则自动处理。
- **US-09** 作为任何使用者，画布中修改后的流程可以导出为 DSL，diff 只反映真实改动。

## 5. 功能需求：DSL 语言（FR-LANG）

> 下文示例使用 YAML 风格的声明式写法以说明信息结构；最终语法形式见 OQ-01。需求约束的是**信息模型与渐进式披露**，不是具体标点。

### 5.1 文件结构

- **FR-LANG-01（P0）** 一个文件包含一个特性（`feature`）及一个或多个场景（`scenarios`）；可选 `background`（同文件所有场景共享的前置步骤）。
- **FR-LANG-02（P0）** 文件头可选声明：`project`（项目 / 模块范围，用于解析 API 路径和上下文），`environment`（默认执行环境）。缺省时取导入时所选范围。
- **FR-LANG-03（P0）** 场景字段：`name`（必填）、`id`（稳定标识，可选，见 FR-GIT-05）、`tags`、`description`（自由文本，进入推导上下文与报告）、`steps`（必填）、`cleanup`（可选）。
- **FR-LANG-04（P0）** 支持注释；键名为固定英文，值（名称、描述、自然语言验证）可用任意语言。是否提供中文键名别名见 OQ-02。
- **FR-LANG-05（P0）** 规模上限与现有模型一致：单场景 ≤100 步骤 / 300 次调用；单文件 ≤50 场景；文件 ≤1 MB。超出报错，不截断。

### 5.2 步骤：渐进式披露的四个层级

每个步骤的唯一必填项是 **API 路径**。其余按需逐级增加：

| 层级 | 使用者写什么 | 平台推导什么 |
|---|---|---|
| **L0 只写路径** | `- POST /orders` | 全部：测试数据、依赖、状态码、提取、鉴权、加解密 |
| **L1 + 验证** | `expect: $.status == "UNPAID"`（或自然语言） | 断言的执行细节；自然语言验证的结构化转换 |
| **L2 + 依赖与关键值** | `with: {amount: 100, orderId: ${order.id}}`、`as: order` | 未指定的其余参数与提取路径 |
| **L3 覆盖项（逃生舱）** | `status: 201`、`headers`、`wait`、`poll`（需授权）、`decode`、`timeout` | 不再推导被覆盖的部分 |

- **FR-LANG-10（P0）路径**：`METHOD /path` 形式；方法在范围内唯一时可省略（`/orders/{id}`）。路径模板参数写 `{name}`；也接受具体路径（`/orders/123`），由平台匹配到模板并把具体值作为锁定输入。
- **FR-LANG-11（P0）路径解析**：在 `project` 范围内按“方法 + 路径模板”精确匹配 API 版本；匹配 0 个报错并给出最接近的候选；匹配多个（多服务同路径）报错并要求加 `service:`。解析结果在转换时**固定为具体分析版本**（项目、分支、提交、方法签名），与现有 API 选择器的固定版本语义一致。
- **FR-LANG-12（P0）步骤名称**：可选 `name`；缺省时用 API 定义中的业务名称（知识卡）或 `METHOD path`。
- **FR-LANG-13（P2）按描述引用 API**：允许写 `call: 申请退款`（无路径），由平台检索 API 定义给出候选，使用者在审阅中选定后**写回为路径**。文件最终存储的始终是路径。

### 5.3 验证（expect）

- **FR-LANG-20（P0）精确断言为主要写法，自然语言为便利写法，可混用**：
  - **精确断言**（确定性解析、直接锁定，**推荐**）：`$.state == "REFUND_PENDING"`、`$.id exists`、`$.items length == 2`。路径基于解包后的业务结构（见 FR-LANG-31）。
  - **自然语言验证**（由平台转换、使用者核对）：`退款单状态为待审核`。转换结果必须以精确断言形式展示（FR-DERIVE-13），使用者对其正确性负责；平台可提示“建议固化为精确断言”。
- **FR-LANG-21（P0）验证对象**：同一 `expect` 中既可以验证回应本身，也可以验证其他系统中的数据。其他系统的验证同样以精确写法为主：
  - `db: orders[id=${order.id}].status == "REFUND_PENDING"`（单表、等值 / 范围过滤，语义对应一条只读查询；使用者不写 SQL，但需要知道表与字段）
  - `redis: order:${order.id} not exists`、`redis: HGET order:${order.id} status == "PAID"`
  - `kafka: order-events key=${order.id} $.type == "REFUND_REQUESTED"`
  - 也可写自然语言（`db: 订单状态变为 REFUND_PENDING`），由平台根据 API 定义的数据影响（第 6 节）与项目背景中的连接推断表、键、主题；推断结果以上述精确形式和等价查询展示；推断不唯一时询问。
  - 连接用逻辑名称引用（`db[orders-db]:`）；同类连接唯一时可省略。
- **FR-LANG-22（P0）默认验证**：未写 `expect` 的步骤，平台只验证“调用成功”（契约声明的成功状态码，及回应包装层的成功标识，若仓库背景中有约定），并作为 GIVEN 步骤处理（见 FR-ROLE-01）。
- **FR-LANG-23（P0）负向预期**：`expect: 拒绝，错误码 AMOUNT_INVALID` 或 `expect: {status: 400, $.code == "AMOUNT_INVALID"}`。负向步骤自动按现有规则截止于该步骤、抑制输出；必须有至少一个业务验证（不能只有状态码）。
- **FR-LANG-24（P0）异步结果**：两种方式，均由使用者显式声明：① **固定等待 + 单次查询**：在查询步骤上声明 `wait: 5s`（≤60 s），等待后只发送一次查询请求并断言；② **授权轮询**：仅当查询步骤的 API 已被使用者授权为可轮询（FR-POLL-01）时，可在该步骤声明 `poll`，按授权的间隔、次数与超时重复发送同一查询，直到本步骤断言满足。未授权的 API 上写 `poll` 是错误。数据层验证在步骤完成（及可选固定等待）后只执行一次；Kafka 验证的观察窗口是对消息的被动监听，不向被测系统发送请求，予以保留。
- **FR-LANG-25（P1）跨步骤一致性**：`退款金额等于订单金额`、`${refund.amount} == ${order.amount}`，映射到步骤分组断言。
- **FR-LANG-26（P1）扩展比较与集合**：`!=`、`>`、`>=`、`<`、`<=`、`contains`、`in`、`length`、“每一项都满足……”（≤1,000 项）。**依赖** FR-DEP-01/02。
- **FR-LANG-27（P0）状态迁移**：`订单从 PAID 变为 REFUND_PENDING` 若平台已有对应状态模型，映射到状态迁移断言；没有时作为普通字段 / 数据层验证处理，并提示可建立状态模型。

### 5.4 依赖（from / 引用）

- **FR-LANG-30（P0）三种精确度，逐级减少推导**：
  1. **字段级显式**：`with: {orderId: ${order.id}}` —— 锁定，不推导；
  2. **步骤级声明**：`from: [order]` —— 只声明“依赖创建订单这一步”，字段对应关系由平台根据双方结构与语义推导；
  3. **完全省略** —— 平台根据目标 API 的必填输入与上游步骤的输出推导；推导出的依赖在审阅中**单独标出**，确认前不能执行。
- **FR-LANG-31（P0）命名**：`as: order` 把该步骤回应的业务主体保存为 `order`，此后可用 `${order.<字段>}` 引用；字段路径基于回应包装层**解包后**的业务结构（使用者不写 `$.data`）。未写 `as` 时，平台默认以步骤名称生成变量名供推导使用。
- **FR-LANG-32（P0）合法性**：只能引用**之前**的步骤；引用不存在的步骤或字段报错；全场景每个上下文值只能有一个生产者（沿用现有约束）。
- **FR-LANG-33（P0）显式值**：`with` 中的字面量（字符串、数字、布尔、null、对象、数组）锁定；未写的参数由平台生成测试数据（第 7 节）。
- **FR-LANG-34（P0）外部值**：`${env.tenant}` 引用项目背景中按环境配置的普通变量；`${secret.payToken}` 引用敏感变量（值在运行时提供，不出现在 DSL）；`${input.xxx}` 声明场景输入（运行时或批量回归时提供）。
- **FR-LANG-35（P0）函数调用**：值可以是函数调用 `${fn.<名称>(<参数>)}`，例如 `${fn.uuid()}`、`${fn.timeShift("yyyy-MM-dd", "P1D")}`、`${fn.digest("SHA-256", ${order.id})}`。参数可以是字面量、上游引用、环境 / 敏感变量或其他函数调用（嵌套 ≤3 层）。函数来自第 9 节的统一目录；未注册的函数名是解析期错误。可用于请求参数、请求头、请求体字段、预期值与数据验证过滤条件，**不能**用于任何控制执行路径的位置（FR-LIN-02）。

### 5.5 覆盖项（L3，可选）

使用者只在平台推导不正确或需要特殊控制时使用：

| 覆盖项 | 作用 | 映射 |
|---|---|---|
| `status` | 预期状态码 | STATUS_EQUALS |
| `headers` / `query` | 显式请求头 / 查询参数 | 输入绑定 |
| `body` | 完整请求体（替代推导） | 输入绑定 |
| `decode` / `encode` | 指定加解密规则名（引用仓库背景中的规则） | 预处理 / 回应解码 |
| `auth` | 指定鉴权方式或身份（引用项目背景中的身份） | 前置 / 请求头 |
| `wait` | 发送本步骤请求前的固定等待（≤60 s），用于等待异步处理 | waitMillis |
| `poll` | 仅限已授权可轮询的 API：`poll: true` 使用授权参数，或 `poll: {every, attempts, within}` 在授权范围内收紧；终止条件为本步骤的 `expect` | FlowNode.poll |
| `role` | 显式 GIVEN / WHEN / THEN | FlowNode.role |

- **FR-LANG-40（P0）** 覆盖项一旦写出即为锁定，平台不再推导该部分；覆盖项值不得包含主机、URL、凭据实际值。

### 5.6 清理与数据驱动

- **FR-LANG-50（P0）清理**：`cleanup` 中列出清理调用（同样只写路径与依赖），按固定顺序在场景结束后执行（执行规则见 FR-LIN-05）；未写时，平台可根据 API 定义中的“逆操作”（如 `DELETE /orders/{id}`）**建议**清理，需确认才生效。
- **FR-LANG-51（P1）数据驱动**：`examples` 表格提供多组 `input` 值，每行一次运行（对应 DataRun）；若某列用于预期值，则每行生成独立测试点。

## 6. 功能需求：API 定义作为上下文工程来源（FR-CTX）

平台推导的质量取决于它对 API 的了解。本节要求把“API 定义”建设为**统一、版本化、可追溯、可由人补充**的知识源，同时服务 DSL、画布补全、整链补全与负向用例建议。

### 6.1 API 定义的组成

每个 API 版本（项目 + 分支 + 提交 + 方法签名 + HTTP 方法 + 路径）的定义包含以下层次。**现状**一列说明平台已经具备的部分：

| 层次 | 内容 | 现状 | 需求 |
|---|---|---|---|
| **A. 结构契约** | 方法、路径、参数位置（path/query/header/body）、类型、必填、请求 / 回应结构、枚举、成功状态码 | 已有：`EndpointContractService` 从分析快照读取 Java 入口与 DTO | **FR-CTX-01（P0）** 作为统一 API 定义的基础层复用；Go 服务通过 go-project-analyzer 提供同等结构（P1） |
| **B. 字段语义** | 字段业务含义、示例值、格式（手机号、金额单位、时间格式） | 部分：`@Schema(description)` | **FR-CTX-02（P0）** 读取 `@Schema`/Javadoc/字段注释（脱敏后）作为语义；**FR-CTX-03（P0）** 支持人在知识卡中补充 |
| **C. 校验约束** | `@NotNull/@Size/@Min/@Max/@Pattern/@Email` 等 | 仅识别 `NotNull/NotBlank/NotEmpty` 为必填 | **FR-CTX-04（P0）** 提取全部 Bean Validation 约束，用于生成合法测试数据与负向用例 |
| **D. 错误语义** | 可能返回的业务错误码、异常与触发条件 | 无 | **FR-CTX-05（P1）** 从入口可达代码中提取抛出的业务异常 / 错误码常量及其条件片段 |
| **E. 副作用与数据影响** | 是否修改数据；写哪些表 / 缓存键 / 消息主题；读哪些 | 无（只有 HTTP 方法） | **FR-CTX-06（P0）** 根据调用链（已有影响分析图）标注：读 / 写、涉及的实体 / 表（JPA `@Table`、MyBatis Mapper）、Redis 键模式、Kafka 主题（`KafkaTemplate.send` 等）；**用于把自然语言数据验证落到正确的对象上** |
| **F. 调用约定** | 鉴权方式、请求加密 / 签名、回应加密、回应包装层（如 `{code,msg,data}`）、分页约定、幂等键 | 部分：仓库背景分析归纳网关过滤器与公共组件；加解密注解只产生警告 | **FR-CTX-07（P0）** 把调用约定结构化为仓库 / 模块级规则（如“`/api/**` 使用 Bearer token，由 `POST /auth/login` 获取”；“回应包装 `Result<T>`，成功码 `0`，业务体在 `data`”），每个 API 继承并可覆盖 |
| **G. 业务关联** | 状态模型、逆操作（创建 ↔ 删除 / 取消）、典型前置（支付前须有订单）、所属业务能力 | 部分：状态模型需人工建立 | **FR-CTX-08（P1）** 从已确认流程、步骤记忆与代码中归纳关联建议，人确认后进入知识卡 |
| **H. 外部定义** | 未被代码分析覆盖的服务、第三方 API | 无 | **FR-CTX-09（P1）** 支持导入 OpenAPI 3 / Swagger 2 文档作为 API 定义来源，与代码推导来源并存并标明来源 |

### 6.2 API 知识卡（人工语义层）

- **FR-CTX-10（P0）** 每个 API 有一张知识卡：业务名称、一句话业务说明、字段语义与示例、调用约定覆盖、前置说明、逆操作、已知限制、轮询授权（FR-POLL-01，仅由使用者设置）。字段均可选。
- **FR-CTX-11（P0）优先级**：人工知识卡 > 仓库 / 模块调用约定规则 > 代码推导事实 > 模型归纳。冲突时展示双方，不静默覆盖。
- **FR-CTX-12（P0）版本跟随**：知识卡按 API 稳定身份（项目 + 方法 + 路径 + 签名）关联，跨提交继承；当新版本的结构契约与知识卡描述的字段不一致时，标记“需复核”，并在推导中降低该项置信度。
- **FR-CTX-13（P1）** 已确认的推导结果（例如“`POST /refunds` 的 `orderId` 来自订单回应的 `id`”）可以一键沉淀到知识卡，减少后续推导与 LLM 调用。

### 6.3 上下文组装

- **FR-CTX-20（P0）按步骤组装**：每个步骤的推导请求只包含：本步骤 API 的完整定义；上游步骤 API 的**回应结构与语义**（用于依赖映射）；下游步骤对本步骤输出的需求（若有）；场景描述与使用者声明；调用约定规则；验证涉及的数据对象结构（第 6.4 节）；相关已确认步骤记忆与知识卡。不包含无关 API 或整个目录。
- **FR-CTX-21（P0）预算与裁剪**：上下文有字符预算（沿用现有源码 48,000 字符 / 20 段上限并扩展到 API 定义）；超出时按“本步骤 > 直接上游 > 约定规则 > 源码片段”的优先级裁剪，并在结果中记录被裁剪的内容。
- **FR-CTX-22（P0）脱敏**：沿用现有规则——主机、URL、实例、凭据、字符串常量与注释中的敏感内容不进入上下文；普通预置测试值不被固化为字面量。
- **FR-CTX-23（P0）可追溯**：每次推导记录上下文包摘要（各组成部分的 ID、版本、哈希），推导结果中的每一项引用其依据（契约字段、知识卡条目、源码证据 ID、约定规则 ID）。
- **FR-CTX-24（P0）失效**：上下文包中任一组成部分版本变化时，依据它的已确认推导标记为过期（与现有步骤记忆的指纹失效机制一致）。

### 6.4 数据对象上下文

- **FR-CTX-30（P0）** 为数据层验证提供对象结构：表 / 集合的字段与类型、主键，Redis 键模式与值结构，消息主题与消息体结构。来源依次为：代码分析（实体、Mapper、迁移脚本、序列化类）、人工补充。**不为获取结构而连接真实数据库**（NG5）。
- **FR-CTX-31（P0）** 数据对象与项目背景中的逻辑连接关联（例如 `orders` 表属于 `orders-db` 连接）；关联缺失时，自然语言数据验证进入“待确认”，不猜测连接。

### 6.5 上下文质量可见

- **FR-CTX-40（P0）完备度**：每个 API 定义显示完备度指标：结构是否完整解析、未解析字段数、是否有语义说明、调用约定是否明确、数据影响是否已知。
- **FR-CTX-41（P0）缺口即问题**：推导时遇到上下文缺口（如加密方式未知、字段含义不明），生成**具体问题**并指向可以补充的位置（知识卡、项目背景、仓库背景），而不是臆造。
- **FR-CTX-42（P1）** 提供“API 定义覆盖率”视图：按项目统计完备度，帮助团队优先补充高频 API。

## 7. 功能需求：推导与转换（FR-DERIVE / FR-CONV）

### 7.1 确定性优先

- **FR-DERIVE-01（P0）** 解析与静态检查完全确定、不调用 LLM：语法、路径解析、引用合法性、单一生产者、规模上限、覆盖项合法性、负向步骤完整性。一次报告全部错误，带行列号、错误码、修复建议。
- **FR-DERIVE-02（P0）** 能用确定性规则得出的推导项不调用 LLM：成功状态码（契约唯一成功码）、鉴权与加解密（调用约定规则）、回应包装解包、名称完全一致且类型相容的依赖字段、精确断言、知识卡与已确认推导的直接复用。
- **FR-DERIVE-03（P0）** 只有剩余部分交给 LLM：测试数据生成、非一致命名的依赖映射、自然语言验证转换、数据对象推断。

### 7.2 各推导项要求

| 推导项 | 要求 |
|---|---|
| **测试数据**（FR-DERIVE-10，P0） | 满足结构与校验约束；遵循字段语义与示例；唯一性字段（如手机号、单号）默认使用生成值避免重复运行冲突；不得使用真实个人信息 |
| **依赖映射**（FR-DERIVE-11，P0） | 只能引用上游输出、场景输入、环境 / 敏感变量；每项给出依据与置信度；低置信度需人选择 |
| **提取路径**（FR-DERIVE-12，P0） | 根据回应结构生成，路径必须在契约中存在（沿用现有“未知回应路径”拒绝规则） |
| **验证转换**（FR-DERIVE-13，P0） | 自然语言 → 精确断言 / 数据层验证计划；结果以精确断言与等价只读查询的形式展示在原文旁（FR-UI-07），由使用者核对；数据层计划遵守现有只读、参数化、上限约束 |
| **鉴权**（FR-DERIVE-14，P0） | 按调用约定规则自动加入鉴权前置（如登录）或请求头；所需身份引用项目背景中的测试身份 / 敏感变量 |
| **加解密与解包**（FR-DERIVE-15，P0） | 按调用约定规则自动加入请求预处理与回应解码；规则缺失而契约提示加密时，作为缺口问题（FR-CTX-41） |
| **异步提示**（FR-DERIVE-16，P0） | API 定义表明异步（202、任务状态字段）时，**提示**使用者增加后续查询步骤，并说明可选择固定等待或（对该查询 API 授权后）轮询；不自动生成重复请求、不自动新增步骤（FR-DERIVE-21）、**不自动授权或建议授权某个 API 为可轮询**，也不在使用者未声明 `poll` 的步骤上加入轮询 |
| **清理建议**（FR-DERIVE-17，P1） | 根据逆操作建议清理，默认不启用 |
| **GWT 角色**（FR-DERIVE-18，P0） | 见 FR-ROLE-01 |

### 7.3 锁定与越界拒绝

- **FR-DERIVE-20（P0）** 声明项（调用顺序、路径、`with` 显式值、依赖、精确断言、自然语言验证原文、覆盖项）不可被改变；LLM 输出若改变它们，该步骤推导无效并报告原因（沿用 FlowFillValidator 的越界拒绝策略）。
- **FR-DERIVE-21（P0）** LLM 不得新增或删除调用步骤；若推导认为缺少前置（例如需要先登录或先创建商品），只能以**建议**形式提出，由使用者决定是否加入 DSL。

### 7.4 转换结果与确认

- **FR-CONV-01（P0）** 转换产出 ordered flow **草稿**；不自动确认、不自动执行；确认流程与其他模式相同。
- **FR-CONV-06（P0）确认即专业责任**：确认表示使用者已核对推导项。平台不提供“全部接受”式的跳过核对：LLM 推导项、低置信度项与推导出的依赖必须在技术视图中逐项查看后才能确认；确定性推导项（契约、规则、知识卡）可按步骤整体确认。确认记录确认人与时间。
- **FR-CONV-02（P0）溯源**：每个节点、输入、断言、预处理、等待都标注来源：`DSL:行号`（声明）、`规则:<ID>`、`知识卡:<ID>`、`契约`、`LLM（置信度）`、`平台默认`。
- **FR-CONV-03（P0）** 确认时记录 DSL 原文哈希与 Flow 哈希；只改注释 / 格式的重导入不产生新修订版。
- **FR-CONV-04（P0）增量**：重导入时未改变的步骤沿用已确认推导，只对变化的步骤及其受影响的下游重新推导。
- **FR-CONV-05（P1）** 允许保存“部分推导”的草稿（待补充项标记），可指派他人补全；补全前不能确认。

### 7.5 双向转换

- **FR-RT-01（P0）** 任意 ordered flow 可渲染为 DSL；渲染时**只输出声明项**（路径、依赖、验证、显式值、被人工修改过的覆盖项），平台可再次推导出的部分不输出，保证 DSL 保持极简。
- **FR-RT-02（P0）** 渲染再导入后，在相同上下文版本下得到哈希相同的 Flow。为此，确认后的推导结果随 Flow 修订版保存，渲染出的 DSL 引用该修订版（而不是每次重新推导）。
- **FR-RT-03（P0）** 输出格式规范化，diff 只反映真实变化；提供格式化命令。
- **FR-RT-04（P1）** 旧版 IR 0.1（DAG）流程不要求支持渲染。
- **FR-RT-05（P0）** 含 PARALLEL 阶段的已有流程不能渲染为 DSL；渲染时报错并说明需改为串行（FR-LIN-01）。

## 8. 功能需求：执行模型与依赖能力

### 8.0 严格线性执行（FR-LIN）

线性是本平台测试**可靠、确定、可复现**的基础，作为强制约束贯穿 DSL、Flow、Test IR 与编译出的 JMX，而不只是 DSL 的语法限制。

- **FR-LIN-01（P0）固定序列**：一个测试点的执行序列（哪些步骤、什么顺序）在确认时完全确定，执行时不随回应内容、函数结果或环境状态改变。DSL 产出的流程只包含 SERIAL 阶段；不支持并行。
- **FR-LIN-02（P0）禁止的构造**：DSL 与推导结果中不得出现：条件分支（if / switch / 按回应选择下一步）、条件跳过、跳转、循环（for / while / foreach / 重复 N 次）、并行、动态生成步骤、按集合元素展开步骤。函数（第 9 节）只能产生值，不能决定是否执行、执行几次或执行哪一步。
- **FR-LIN-03（P0）LLM 同样受约束**：LLM 推导不得新增、删除、重排步骤（FR-DERIVE-21），不得引入上述构造；违反时整个推导结果被拒绝。
- **FR-LIN-04（P0）默认每个请求恰好发送一次**：一次运行中，每个步骤的 HTTP 请求默认只发送一次；失败自动重试、“直到满足为止”和任何其他重复发送均被禁止。理由：平台无法仅凭单次调用的上下文可靠判断 API 是否幂等，重复请求可能产生非预期副作用（重复下单、重复扣款、状态多次推进），破坏确定性与可重复性。
  - **唯一例外是授权轮询**（FR-POLL）：使用者明确授权为可轮询的 API，且步骤显式声明了 `poll`；
  - 执行器层面不对业务请求做传输重试（连接失败直接判定 INCONCLUSIVE），避免“请求已到达但回应丢失”时重复发送；轮询步骤中单次尝试的连接失败同样终止该步骤，不计为“未满足、继续轮询”；
  - 轮询仍是**单个步骤内**对同一请求的有界重复，不改变步骤序列，不构成流程级循环（FR-LIN-02 不变）。
- **FR-POLL-01（P0）按 API 显式授权**：可轮询性是使用者对**某个具体 API**（项目 + 方法 + 路径 + 方法签名的稳定身份）的显式授权，而不是平台推断。授权记录包含：固定间隔（200 ms–30 s）、最大尝试次数（≤120）、总超时（1–300 s）、授权理由（例如“异步导出任务状态查询接口”）、授权人与时间。授权保存在 API 知识卡中，随 API 定义版本跟随。
- **FR-POLL-02（P0）禁止推断**：平台与 LLM 不得根据 HTTP 方法（GET / HEAD）、只读或副作用标注（FR-CTX-06）、API 文档、命名（如 `/status`）、历史流程或任何其他信号推断某个 API 可轮询，也不得自动创建、建议创建或扩大授权。界面中授权必须由使用者在该 API 上单独操作完成，不提供批量授权。
- **FR-POLL-03（P0）步骤级显式使用**：授权只是允许；步骤仍须在 DSL 或画布中显式声明 `poll` 才会轮询。步骤的轮询参数只能等于或严于授权参数（间隔不小于、次数与超时不大于授权值）。终止条件只能是本步骤自身的 `expect`；达到次数或超时仍未满足 → 该步骤断言失败（按角色判定，FR-ROLE-03）。LLM 推导不得在步骤上加入或修改 `poll`（属于声明项，FR-DERIVE-20）。
- **FR-POLL-04（P0）固定与失效**：流程确认时固定所用授权（授权 ID + 参数 + 版本），纳入 Flow 哈希。授权被撤销、参数被收紧到低于步骤参数，或 API 结构契约发生变化而授权被标记“需复核”时，引用该授权的已确认流程不能执行（判定 INCONCLUSIVE，原因“轮询授权失效”），需重新确认。
- **FR-POLL-05（P0）记录与展示**：运行记录每个轮询步骤的实际尝试次数、每次尝试的状态码与终止原因；技术视图与报告显示所用授权、参数与授权人。
- **FR-POLL-06（P0）现有能力兼容**：Phase 2.1 已实现的 `FlowNode.poll` / `http.poll` 作为本机制的执行实现保留。已确认的含 poll 流程：其 API 若已有授权且参数在授权范围内，照常执行；否则提示补充授权，补充前判定 INCONCLUSIVE（原因“缺少轮询授权”）。画布新增 poll 时同样要求 API 已授权。
- **FR-LIN-05（P0）失败即停止**：任一步骤失败时，后续业务步骤一律不执行（现有“错误即停止线程”语义）；清理按声明的固定逆序执行，只处理已实际产生资源的清理调用，其依据是确定的执行状态而不是条件逻辑。
- **FR-LIN-06（P0）编译产物校验**：编译器只输出白名单内的 JMeter 元素：单线程、单次迭代的线程组；HTTP 采样器；平台固定模板的 JSR223 前 / 后处理器；平台管理的函数调用；固定等待所需的定时器；**仅在授权轮询步骤中**使用的轮询控制器（While + 固定定时器，次数与超时由授权参数约束）。出现其他逻辑控制器（If、非轮询用途的 While、Loop、ForEach、Switch、Runtime、Throughput、Random 等）或采样器重试配置即编译失败；该校验作为测试纳入 CI。
- **FR-LIN-07（P0）数据驱动不破坏线性**：`examples` 的每一行是一次**独立**的线性运行，行之间不共享上下文、不相互依赖。
- **FR-LIN-08（P0）复现所需记录**：每次运行记录：流程修订版与哈希、函数与工具目录版本及实现指纹、每个非敏感函数的实际返回值、随机种子（若使用）、每个请求的发送次数（非轮询步骤必须为 0 或 1；授权轮询步骤不超过授权的最大次数）、所用轮询授权。凭这些记录可以解释任意一次运行的每个输入值从何而来。

### 8.1 GWT 角色与判定（FR-ROLE）

- **FR-ROLE-01（P0）角色推导**：使用者可不写角色。默认规则：第一个写了 `expect` 的步骤之前的步骤为 GIVEN；从该步骤起，修改型步骤为 WHEN；最后一个 WHEN 之后的只读步骤为 THEN。没有任何 `expect` 时，最后一个步骤为 WHEN。推导结果在审阅中展示，可用 `role` 覆盖。（规则细节在设计阶段以样例集校准，见 OQ-04。）
- **FR-ROLE-02（P0）结构**：顺序必须为 GIVEN* → WHEN+ → THEN*；至少一个 WHEN。
- **FR-ROLE-03（P0）判定**：GIVEN 步骤失败 → **INCONCLUSIVE**（“前置未建立”，标出步骤）；WHEN / THEN 业务验证失败 → **FAIL**；基础设施问题 → INCONCLUSIVE。
- **FR-ROLE-04（P0）** THEN 步骤必须只读：依据 API 定义的副作用标注（FR-CTX-06），而不只是 HTTP 方法；标注未知时提示确认。
- **FR-ROLE-05（P0）兼容**：已有流程视为 WHEN，判定结果不变；角色为空时不改变已有哈希。
- **FR-ROLE-06（P1）** 批量回归、Gerrit 评论、AI 失败分析区分“前置未建立”与“产品失败”。

### 8.2 节点内部管线（FR-PIPE）

- **FR-PIPE-01（P0）** 交易节点内部固定顺序：构造请求 → （可选固定等待）→ 执行（恰好一次；授权轮询步骤为有界重复）→ 解码 / 解包回应 → 提取输出 → 断言 → 数据一致性验证 → 提交输出。使用者不配置顺序。
- **FR-PIPE-02（P0）** 每个阶段只使用第 9 节的封闭、版本化函数与工具目录，不支持任意脚本。
- **FR-PIPE-03（P0）** 输出仅在本节点全部检查通过后提交（现有原子语义）。
- **FR-PIPE-04（P1）** 报告按阶段展示失败位置，AI 失败分析使用阶段信息。

### 8.3 回应解码（FR-DEC）

- **FR-DEC-01（P0）** 新增回应解码阶段，与请求预处理对称：`platform.decrypt@1`、`base64.decode@1`、`json.parse@1`、`envelope.unwrap@1`。
- **FR-DEC-02（P0）** 由调用约定规则自动配置（FR-DERIVE-15），使用者不需要编写；审阅中显示所应用的规则名称与作用（如“回应经 AES 解密后按 `Result<T>` 解包，业务体取自 `data`”）。
- **FR-DEC-03（P0）** 密钥只来自敏感变量；解码失败计为该节点失败；回应原文不进入报告与 JTL。

### 8.4 可复用前置（FR-FIX）

- **FR-FIX-01（P0）鉴权前置自动化**：调用约定中声明的鉴权流程（如登录获取 token）作为平台管理的前置自动插入，使用者无需在每个场景中写登录。
- **FR-FIX-02（P1）通用前置**：版本化、带参数、带输出与清理的步骤序列（如“创建已支付订单”），可在 DSL 中以 `use: paid-order` 引用；生成场景时展开为普通节点并标注来源。
- **FR-FIX-03（P1）** 前置中的 API 受变更影响时，引用它的测试点进入回归选择。

### 8.5 断言扩展（FR-DEP）

- **FR-DEP-01（P1）** JSON 断言新增 NE、GT、GE、LT、LE、CONTAINS、IN、LENGTH_EQUALS。
- **FR-DEP-02（P1）** 新增 EACH 集合断言（≤1,000 项）。

## 9. 功能需求：JMeter 扩展与工具目录（FR-FN / FR-EXT）

### 9.1 背景

现有请求预处理已有一份封闭的工具目录（`time.now@1`、`uuid@1`、`digest@1`、`platform.encrypt@1`、`platform.sign@1` 等），同时供 UI 与 LLM 使用，由固定 JSR223 模板执行；为安全起见，目前**不**把模型文本拼进 `${__function(...)}`，也不开放任意函数名。团队在 JMeter 中常用内置函数（`__time`、`__UUID`、`__digest`、`__timeShift`、`__RandomString` 等），也需要项目专有的逻辑（签名、加解密、编码、测试数据生成）。本节要求：基于 **JMeter 自身的扩展规范**，允许用户编写 Java 扩展、打包为 JAR 上传到平台，并通过平台定义的**标准元数据契约**自动注册为工具；与平台工具、JMeter 内置函数一起组成统一目录，暴露给 LLM 发现与调用。全部能力在**保持严格线性**和现有安全边界的前提下提供。

### 9.2 统一目录

- **FR-FN-01（P0）一个目录，三类实现**：目录中的每个条目以 `名称@版本` 标识，实现类型为：
  1. **平台工具**：现有请求预处理工具，原样迁入；
  2. **JMeter 内置函数**：白名单中的内置函数（FR-FN-06）；
  3. **用户扩展**：用户上传的 JAR 中、按 9.4 契约声明的 JMeter 扩展。
  DSL、画布、LLM 看到的是同一种条目，不区分实现类型；`${fn.digest(...)}` 由目录解析到具体实现。
- **FR-FN-02（P0）条目元数据**：每个条目必须具备以下元数据（用户扩展由 9.4 的注解契约提供并在上传时自动解析；平台工具与内置函数由平台维护同结构的元数据）：
  - 名称、版本、一句话用途、详细说明（何时使用、何时不应使用）；
  - 参数：名称、类型（string / integer / number / boolean / object）、是否必填、取值约束（枚举、格式、范围）、是否敏感；
  - 返回值：类型、格式说明、是否敏感；
  - **确定性类别**：`PURE`（相同输入恒得相同输出）、`CLOCK`（依赖当前时间）、`RANDOM`（随机，可声明是否支持种子）；
  - 可用位置：请求值、预期值、数据验证过滤条件（可多选）；
  - 至少 2 个示例（输入 → 输出；`CLOCK` / `RANDOM` 给出输出格式示例）；
  - 实现指纹（JAR 摘要或平台工具版本）、提供者、变更说明。
- **FR-FN-03（P0）版本固定**：流程确认时固定所用条目的 `名称@版本` 与实现指纹，并纳入 Flow 哈希与能力锁；执行前检查 JMeter 安装中的实现指纹一致，不一致则运行判定为 INCONCLUSIVE（环境不匹配），不静默使用其他版本。
- **FR-FN-04（P0）兼容**：现有使用预处理工具的流程哈希与行为不变；目录迁移不得改变已有工具的 ID、版本与参数。
- **FR-FN-05（P0）目录接口**：在现有 `GET /api/business-testing/preparation-tools` 基础上提供统一目录查询（列表、按关键词 / 类别检索、按名称取详情），与 LLM 工具使用同一数据源。

### 9.3 可纳入的函数：线性与安全约束

- **FR-FN-06（P0）只允许“计算值”的函数**：可纳入目录的函数必须只根据参数计算并返回一个值。以下函数**不得**纳入（内置函数按此规则形成白名单，具体清单在设计阶段确定）：
  - 执行任意代码或表达式：`__groovy`、`__javaScript`、`__BeanShell`、`__jexl2/3`、`__eval`、`__evalVar`；
  - 修改变量、属性或线程间共享状态：`__setProperty`、`__split`（写变量）、`__V`（动态变量名）、`__counter`（跨迭代状态）；
  - 读取文件系统或外部资源：`__CSVRead`、`__StringFromFile`、`__FileToString`、`__XPath`（读文件）；
  - 暴露执行环境：`__machineIP`、`__machineName`、`__TestPlanName`、`__threadNum`；
  - 条件或控制类：`__if`、`__isVarDefined`、`__isPropDefined`，以及任何会影响执行路径的函数。
- **FR-FN-07（P0）不能影响执行路径**：函数结果只能作为请求值、预期值或数据验证参数；不能作为任何执行条件（FR-LIN-02）。
- **FR-FN-08（P0）不由文本拼接调用**：编译器根据结构化调用（名称、版本、类型化参数）生成 JMX 中的函数调用，负责 JMeter 函数语法的转义（逗号、反斜杠、`${}`）；LLM 或使用者提供的文本永远不会被直接拼接进 `${__...}` 字符串。
- **FR-FN-09（P0）敏感值**：敏感参数只能绑定敏感变量；敏感返回值不进入报告、日志、JTL、步骤记忆与 LLM 上下文；声明为敏感的函数不能用于预期值展示。

### 9.4 用户扩展：基于 JMeter 规范的 JAR 扩展机制（FR-EXT）

#### 9.4.1 扩展点与 JMeter 规范

- **FR-EXT-01（P0）扩展点**：MVP 只接受 JMeter **函数**扩展：实现 `org.apache.jmeter.functions.Function`（通常继承 `AbstractFunction`），由 JMeter 按其规范发现与调用。选择函数作为唯一扩展点的原因：它天然只“计算并返回一个值”，最容易保持严格线性与确定性。
- **FR-EXT-02（P0）阶段**：扩展通过元数据声明可用阶段，由平台固定模板在节点内部管线（FR-PIPE-01）的对应位置调用：
  | 阶段 | 用途 | 输入 | 输出 |
  |---|---|---|---|
  | `REQUEST_VALUE` | 计算单个请求值（字段、请求头、查询参数） | 参数 | 标量 |
  | `REQUEST_TRANSFORM` | 变换整个请求（加密、签名） | 请求体 / 请求头作为**显式参数**传入 | 新的请求体或请求头 |
  | `RESPONSE_DECODE` | 解码回应（解密、解包、格式转换） | 回应体作为**显式参数**传入 | 解码后的回应体 |
  | `EXPECTED_VALUE` | 计算预期值或数据验证参数 | 参数 | 标量 |
  扩展只能从参数获取输入，不得自行读取 JMeter 变量、上一个采样结果或属性；所需数据都由平台模板以参数传入。这使扩展的行为只取决于其参数，可单独测试与复现。
- **FR-EXT-03（P0）不接受的扩展类型**：采样器（Sampler）、逻辑控制器（Controller）、定时器（Timer）、监听器（Listener）、配置元件（ConfigElement）、线程组——它们会改变请求数量、执行路径或时序，与严格线性约束冲突，**永久不接受**。断言（Assertion）与前 / 后置处理器（Pre/PostProcessor）的需求已由 `EXPECTED_VALUE`、`REQUEST_TRANSFORM`、`RESPONSE_DECODE` 阶段覆盖，**本期不开放**（已决事项 D-03）；未来有明确需求时再评估。
- **FR-EXT-04（P0）JMeter 合规要求**（上传时校验）：
  - 实现类为 `public`、有公共无参构造器，实现 `Function` 接口；
  - 符合 JMeter 函数发现规则：类的全限定名包含 `.functions.` 且不包含 `.gui.`；
  - `getReferenceKey()` 返回 `__` 开头的唯一键，与元数据声明一致，不与内置函数或其他扩展冲突；
  - `getArgumentDesc()` 的数量与元数据声明的参数一致；`setParameters` 的最少 / 最多参数个数与必填参数一致；
  - 字节码版本不高于运行器 JVM；JAR 不包含 `org.apache.jmeter.*`、`io.yuan.octopus.*`、`java.*` 等保留包，不包含本地库；
  - 第三方依赖须重定位（shade）到扩展自己的包下，或只使用 JMeter 自带库，避免与 JMeter 及其他扩展冲突。

#### 9.4.2 标准元数据契约

- **FR-EXT-10（P0）SDK**：平台提供轻量 SDK（仅编译期依赖，不引入运行时依赖），包含元数据注解与可选基类。开发者在符合 JMeter 规范的函数类上添加注解即可完成注册所需的全部声明，不需要另写配置文件。
- **FR-EXT-11（P0）注解契约**（命名示意，具体在设计阶段确定）：
  | 注解 | 位置 | 内容 |
  |---|---|---|
  | `@OctopusTool` | 类 | `name`（命名空间.名称，如 `acme.sign`）、`version`（语义化版本）、`displayName`、`summary`（一句话用途，≤120 字符）、`description`（详细说明，≤2,000 字符）、`whenToUse`、`whenNotToUse`、`category`、`tags`、`determinism`（PURE / CLOCK / RANDOM）、`seedParam`（RANDOM 可选）、`stages`、`sensitiveOutput`、`owner`、`deprecated` |
  | `@ToolParam`（可重复） | 类 | `index`（对应 JMeter 参数位置）、`name`、`type`（string / integer / number / boolean / object）、`required`、`defaultValue`、`description`、约束（`enumValues`、`pattern`、`min`、`max`、`format`、`maxLength`）、`sensitive`、`example` |
  | `@ToolOutput` | 类 | `type`、`format`、`description`、`schema`（输出为 object 时的 JSON Schema） |
  | `@ToolExample`（可重复） | 类 | `args`、`output`（PURE 为精确值，CLOCK / RANDOM 为格式模式）、`description` |
  | `@ToolError`（可重复） | 类 | `code`、`description`（何种输入导致该错误、如何修正） |
  说明类字段支持中文与英文，可只提供一种。
- **FR-EXT-12（P0）可选基类**：SDK 提供继承自 `AbstractFunction` 的基类，按注解自动完成：参数个数检查、类型转换与约束校验、`getReferenceKey` / `getArgumentDesc` 生成、输出序列化（object 输出为 JSON 字符串）、异常到 `@ToolError` 错误码的映射。开发者只需实现一个类型化的计算方法。不使用基类、直接继承 `AbstractFunction` 也允许，只要通过 FR-EXT-04 与 FR-EXT-21 的一致性校验。
- **FR-EXT-13（P0）面向人与 LLM 的结构**：元数据字段的划分本身服务于两类读者：
  - `summary` / `category` / `tags` 用于检索结果列表（`search_functions`）；
  - `description` / `whenToUse` / `whenNotToUse` / `@ToolError` 用于判断“该不该用、何时不该用”；
  - `@ToolParam` / `@ToolOutput` 可以无损转换为 **JSON Schema**，直接作为 LLM 工具调用的参数定义，也用于服务端校验；
  - `@ToolExample` 同时是文档示例、LLM 少样本示例与注册测试用例。
- **FR-EXT-14（P0）同源渲染**：平台从同一份解析结果确定性地生成：① 人阅读的扩展文档页（参数表、示例、错误码、确定性、阶段、所有者、版本历史）；② LLM 工具定义（名称、描述文本、参数 JSON Schema）。两者不会不一致；单个工具定义有长度预算（`describe_function` 结果 ≤ 约 1,500 token），超出时上传即提示精简说明。

#### 9.4.3 上传、解析与注册流程

- **FR-EXT-20（P0）上传**：在平台上传单个 JAR（≤20 MB），一个 JAR 可包含多个扩展；记录上传人、时间、SHA-256。
- **FR-EXT-21（P0）静态解析，不执行代码**：平台读取字节码与注解自动识别扩展及其元数据，**不在平台进程中加载类或执行静态初始化**。解析结果以“草稿条目”展示。没有 `@OctopusTool` 注解的函数类会被列出但不能注册。
- **FR-EXT-22（P0）元数据质量检查**：必填字段齐全；每个参数都有说明；至少 2 个示例且覆盖全部必填参数；PURE 扩展的示例为精确输出；约束合法（正则可编译、枚举非空、范围有效）；阶段与确定性组合合法（`EXPECTED_VALUE` 只允许 PURE）；示例中敏感参数不得含真实值；字段长度在预算内。不满足即逐项报错，指出注解与字段。
- **FR-EXT-23（P0）风险扫描**：扫描字节码中的危险调用：进程执行（`Runtime.exec`、`ProcessBuilder`）、`System.exit`、网络（`java.net.*`、HTTP 客户端）→ **直接拒绝**；文件读写、反射与 `setAccessible`、`System.setProperty`、线程创建、写 JMeter 变量 / 属性（`JMeterVariables.put`、`JMeterUtils.setProperty`）、读取上一个采样结果 → **标记为风险警告**：不阻止注册，但在上传结果、扩展文档页与 LLM 工具定义的元数据中显示（LLM 不会因此改变行为，警告供使用者知情）。
- **FR-EXT-24（P0）隔离验证**：在隔离的 JMeter 子进程中（无网络、受限文件系统、超时）完成：按 JMeter 规范发现该函数；核对引用键与参数描述；执行全部示例并比对输出；PURE 扩展对每个示例执行两次确认结果一致；单次调用耗时上限（默认 100 ms）；错误输入返回声明的错误码。任一失败即拒绝注册。
- **FR-EXT-25（P0）自动注册，无人工审核**：本期不设审核流程或职责分离。FR-EXT-04 合规校验、FR-EXT-22 元数据契约校验、FR-EXT-23 安全扫描（拒绝项）与 FR-EXT-24 隔离测试全部通过后，上传者即可直接发布注册；任一失败则不能发布。记录上传 / 发布人、时间、JAR 摘要与全部校验结果，供追溯。可限定适用的项目 / 模块。
- **FR-EXT-26（P0）版本不可变与共存**：已发布的版本不可修改；同名同版本但内容不同的 JAR 被拒绝。已确认流程固定在具体版本，不同版本需能在同一 JMeter 安装中共存：引用键与实现类的包名必须包含版本标识（平台校验），依赖须重定位到对应版本的包下。
- **FR-EXT-27（P0）停用与弃用**：可停用某版本（新推导不再选用，已确认流程仍按固定版本运行并在报告中提示）；可标记弃用并指向替代版本。
- **FR-EXT-30（P0）运行时不隔离**：本期扩展在执行时与 JMeter 运行在同一进程，不施加运行时权限限制或沙箱；安全控制集中在上传阶段（FR-EXT-21–24）。运行时隔离留待后续版本按需评估（已决事项 D-02）。
- **FR-EXT-28（P0）分发与校验**：已发布的扩展随运行器的 JMeter 安装部署；运行前校验所需扩展及其 SHA-256 指纹（FR-FN-03）；平台不在运行时下载代码。
- **FR-EXT-29（P1）开发者工具**：提供扩展模板工程（Gradle / Maven）与本地校验命令（与平台执行相同的 FR-EXT-04、FR-EXT-22–24 检查），使开发者在上传前发现问题。

### 9.5 作为 LLM 工具：发现与使用

- **FR-FN-20（P0）按需发现，而非全量注入**：推导时 LLM 不在提示中收到完整目录，而是通过工具调用按需发现：
  - `search_functions(query, position?)`：按用途关键词与可用位置检索，返回名称、版本、一句话用途、确定性类别；
  - `describe_function(name@version)`：返回完整清单（参数、返回、约束、示例、何时不应使用）。
  每次推导的工具调用次数有上限（默认 10 次），超出即结束发现阶段。
- **FR-FN-21（P0）上下文提示**：上下文组装（FR-CTX-20）可以根据调用约定与 API 定义**预先推荐**少量相关函数（例如调用约定要求签名时推荐对应签名函数），作为发现的起点。
- **FR-FN-22（P0）结构化使用**：LLM 只能以 `{function: 名称@版本, args: {...}}` 的结构化形式使用函数，参数来源限于字面量、上游引用、环境 / 敏感变量、其他函数结果；服务端按清单校验参数类型、必填、约束、可用位置与确定性规则，失败则拒绝该推导项。
- **FR-FN-23（P0）确定性偏好**：同等可行时优先使用 `PURE` 函数；用于**预期值**的函数必须为 `PURE`（预期值不得依赖时间或随机数，否则测试不可复现）；`RANDOM` 函数只用于需要唯一性的输入（如单号、手机号），并按 FR-FN-24 记录。
- **FR-FN-24（P0）随机与时间的可复现**：`RANDOM` 函数若支持种子，平台为每次运行注入运行种子并记录；所有非敏感函数的实际返回值记录到运行报告（FR-LIN-08）。
- **FR-FN-25（P0）调用（试算）**：LLM 可调用 `try_function(name@version, args)` 实际执行 `PURE` 条目，用于核对推导出的预期值或检查参数格式；只允许字面量与已知的普通测试值作为参数（不允许敏感变量），在与 FR-EXT-24 相同的隔离环境中执行，有超时与每次推导的次数上限（默认 5 次）。`CLOCK` / `RANDOM` 条目不可试算。试算结果只用于推导，不直接作为预期值写入（预期值仍以函数调用形式保存，运行时计算）。
- **FR-FN-26（P0）可审阅**：技术视图（FR-UI-07）显示每个函数调用的名称、版本、参数来源、确定性类别，以及（`PURE` 函数且无敏感参数时）预览结果；LLM 选用的函数属于需逐项核对的推导项（FR-CONV-06）。
- **FR-FN-27（P0）度量**：记录函数发现调用次数、被选用的函数、被人工替换或删除的比例，纳入 LLM 建议度量。

## 10. 存储与 git 同步（FR-GIT）

- **FR-GIT-01（P0）** 平台中已确认的 Flow 修订版是执行依据；DSL 是可读表示与编写入口。
- **FR-GIT-02（P0）** 支持单文件与目录批量导入、按项目或标签导出。
- **FR-GIT-03（P1）** 可为项目配置仓库内测试目录与分支；平台定期或经 webhook 读取并导入为草稿；平台确认的修订版可生成 PR / 补丁，不直接推送受保护分支。
- **FR-GIT-04（P1）** 双方都修改同一场景时标记冲突并展示 diff，由人选择。
- **FR-GIT-05（P0）** 每个场景有稳定 ID（显式 `id`，缺省时由文件路径 + 场景名生成），用于重导入匹配与历史追踪。
- **FR-GIT-06（P1）CLI**：`lint`（本地离线，只做语法与结构检查）、`check --server`（含路径解析与依赖校验）、`run --tags --env`（发起批量运行并等待，非 0 退出码表示失败）。

## 11. 编辑与审阅界面（FR-UI）

- **FR-UI-01（P0）** DSL 编辑器：语法高亮、实时诊断、格式化。
- **FR-UI-02（P0）** 路径补全：输入路径或业务关键词即检索 API 定义，候选显示业务名称、说明、完备度。
- **FR-UI-03（P1）** 依赖补全：输入 `${` 时列出上游步骤及其（解包后的）回应字段与语义。
- **FR-UI-04（P0）审阅视图**：左侧 DSL，右侧推导出的流程；每个推导项按来源着色并显示依据与置信度；低置信度与缺口问题集中列出，可就地回答或跳转到知识卡 / 背景补充。
- **FR-UI-07（P0）技术视图（面向 4.1 基线）**：审阅中每个步骤都能展开查看以使用者熟悉的技术形式呈现的推导结果，供专业判断：
  - **请求示例**：方法、路径、查询参数、请求头（敏感值打码）、请求体（加密前的明文结构），以及标明哪些值来自依赖、哪些是生成值；
  - **依赖映射**：`上游步骤.字段 → 本步骤参数位置.字段`，含类型；
  - **断言**：精确断言形式（JSON 路径 + 运算 + 预期值），自然语言验证旁显示其转换结果；
  - **数据验证**：等价的只读查询（如 `SELECT status FROM orders WHERE id = ?`、`HGET order:{id} status`）、所用逻辑连接与等待时间（Kafka 为观察窗口）；
  - **调用约定**：应用的鉴权、加解密、解包规则名称与作用；
  - **等待**：固定等待时长及其来源。
  技术视图使用通用术语（HTTP、JSON 路径、SQL），**不**暴露平台内部模型（Binding 来源、IR 字段名、工具编号、JMX 结构）。
- **FR-UI-08（P0）** 诊断与问题信息使用面向工程师的准确技术表述（例如“`POST /refunds` 的 body 字段 `orderId`（integer，必填）没有来源”），不为降低门槛而模糊化；同时不出现内部类名与堆栈。
- **FR-UI-05（P0）** 画布与 DSL 视图可切换编辑。
- **FR-UI-06（P0）** API 知识卡编辑界面，显示代码推导事实与人工补充的对比、完备度与“需复核”标记。

## 15. 验收标准（节选）

- **AC-LANG-01** 假如 DSL 只有 `POST /orders`、`POST /orders/{id}/pay`、`POST /refunds` 三行和退款步骤的 `$.state == "REFUND_PENDING"`，当转换，那么得到草稿：测试数据满足约束，`{id}` 与 `orderId` 自动依赖订单回应，鉴权自动插入，最后一步为 WHEN，所有推导项都有来源；推导出的依赖在技术视图逐项查看前不能确认。
- **AC-UI-01** 假如使用者写了 `db: 订单状态变为 REFUND_PENDING`，当查看技术视图，那么显示等价只读查询、逻辑连接与对应的精确写法，且不出现平台内部字段名。
- **AC-LANG-02** 假如步骤写了 `with: {orderId: ${order.id}, reason: "质量问题"}`，当 LLM 推导试图修改 `reason`，那么该步骤推导被拒绝并显示原因。
- **AC-LANG-03** 假如路径 `/orders` 在范围内被两个服务暴露，当 lint，那么报错并要求指定 `service`。
- **AC-CTX-01** 假如 `POST /refunds` 的调用链写入 `refund` 表，当使用者写 `db: 退款记录已创建`，那么平台把验证落到 `refund` 表及其所属连接，并在审阅中显示依据（调用链与实体映射）。
- **AC-CTX-02** 假如契约提示接口加密，但仓库背景中没有加解密规则，当转换，那么产生缺口问题“缺少回应加解密规则”并指向补充位置，而不是生成不可执行的步骤。
- **AC-CTX-03** 假如知识卡说明 `amount` 单位为“分”，当生成测试数据，那么金额使用整数分值；知识卡修改后，相关已确认推导标记为过期。
- **AC-DERIVE-01** 假如上游字段与下游必填参数同名同类型，当转换，那么依赖映射由确定性规则完成，不调用 LLM。
- **AC-ROLE-01** 假如 GIVEN 步骤“创建订单”返回 409，当执行结束，那么判定 INCONCLUSIVE（前置未建立），批量回归不计为失败。
- **AC-RT-01** 假如已确认的 ordered flow，当渲染为 DSL，那么输出只包含声明项；再导入得到哈希相同的 Flow。
- **AC-LIN-01** 假如 LLM 推导结果中出现新的步骤、按回应条件跳过某步骤或重复某步骤，当服务端校验，那么整个推导结果被拒绝并说明违反了严格线性约束。
- **AC-LIN-02** 假如编译出的 JMX 中出现白名单以外的逻辑控制器，当编译，那么编译失败。
- **AC-LIN-03** 假如同一修订版运行 10 次，当比较执行记录，那么每次执行的步骤序列完全相同；函数返回值可从运行报告中逐一查到。
- **AC-FN-01** 假如调用约定要求 SHA-256 签名，当推导，那么 LLM 通过 `search_functions` 找到并使用目录中的签名函数，技术视图显示函数名称、版本与参数来源。
- **AC-FN-02** 假如 LLM 试图在预期值中使用 `CLOCK` 或 `RANDOM` 函数，当校验，那么该推导项被拒绝。
- **AC-FN-03** 假如上传的扩展 `@ToolExample` 输出与实际执行结果不一致，当注册，那么注册被拒绝并显示哪个示例不符。
- **AC-EXT-01** 假如上传的 JAR 中一个类继承 `AbstractFunction` 并带有完整 `@OctopusTool` / `@ToolParam` / `@ToolOutput` / `@ToolExample` 注解，当上传，那么平台不执行任何代码即生成草稿条目，展示参数、输出、阶段、确定性与说明。
- **AC-EXT-02** 假如扩展类的包名不包含 `.functions.`，或 `getArgumentDesc()` 数量与 `@ToolParam` 不一致，当注册，那么被拒绝并指出不符合的 JMeter 规范项。
- **AC-EXT-03** 假如扩展字节码中调用了 `ProcessBuilder` 或 `java.net.Socket`，当上传，那么直接拒绝。
- **AC-EXT-04** 假如扩展已发布，当 LLM 推导调用 `describe_function`，那么返回的参数 JSON Schema、说明与示例与人看到的文档页来自同一份元数据且内容一致。
- **AC-EXT-05** 假如 `acme.sign@1.0.0` 与 `acme.sign@2.0.0` 同时发布，当分别固定在两个流程中运行，那么两者在同一 JMeter 安装中各自使用正确版本。
- **AC-LIN-04** 假如同一修订版的任意一次运行，当检查执行记录，那么非轮询步骤的每个业务请求发送次数为 0 或 1，不存在重试。
- **AC-POLL-01** 假如 `GET /exports/{id}` 没有轮询授权，当 DSL 在该步骤写 `poll: true`，那么 lint 报错“该 API 未授权轮询”；LLM 推导也不会建议授权。
- **AC-POLL-02** 假如使用者授权 `GET /exports/{id}` 每 2 s、最多 30 次、超时 60 s，当步骤声明 `poll: {every: 1s}`，那么报错“间隔不得小于授权值”；声明 `poll: true` 时按授权参数执行，第 30 次仍未满足即该步骤失败。
- **AC-POLL-03** 假如某个 GET 接口在契约中标注为只读、路径为 `/status`，当转换，那么平台不会为其加入轮询，也不会提示“可授权轮询”。
- **AC-POLL-04** 假如轮询授权被撤销，当运行引用它的已确认流程，那么判定 INCONCLUSIVE（轮询授权失效），不发送请求。
- **AC-EXT-06** 假如上传的 JAR 通过全部自动校验，当上传者点击发布，那么扩展立即注册并可被 LLM 发现，无需他人审核；若扫描发现 `ProcessBuilder`，则无法发布。
- **AC-FN-04** 假如运行环境中的函数 JAR 指纹与流程固定的不一致，当执行，那么运行判定为 INCONCLUSIVE（环境不匹配），不发送任何请求。
- **AC-FN-05** 假如参数中含逗号与 `${` 的字面量，当编译为 JMeter 函数调用，那么转义正确，函数收到的参数与声明完全一致。
- **AC-GIT-01** 假如 CI 运行 `lint`，当存在错误，那么退出码非 0 且诊断与编辑器一致。

## 18. 示例（YAML 风格示意）

### 18.1 最小写法（L0 + L1）

```yaml
feature: 退款
project: shop-platform/order-service

scenarios:
  - name: 已支付订单可以申请退款
    tags: [refund, smoke]
    steps:
      - POST /orders
      - POST /orders/{id}/pay
      - call: POST /refunds
        expect:
          - $.state == "REFUND_PENDING"
          - db: 订单状态变为 REFUND_PENDING     # 便利写法，审阅中显示等价查询
```

平台推导：创建订单的测试数据；`{id}` 与退款的 `orderId` 来自订单回应；登录前置与 token；成功状态码；回应包装解包；前两步为 GIVEN、退款为 WHEN；第二条验证转换为 `orders` 表只读校验。技术视图示意：

```text
POST /refunds        body: {"orderId": ← order.id (integer), "reason": "test-<runId>"}   [依赖: 推导, 待核对]
  status == 200                                    [契约]
  $.state == "REFUND_PENDING"                      [DSL:13]
  db[orders-db]: SELECT status FROM orders WHERE id = :order.id  → == "REFUND_PENDING"   [LLM, 高, 依据: 调用链 + @Table(orders)]
  约定: Bearer token（规则 auth.login）、回应按 Result<T> 解包（规则 envelope.result）
```

### 18.2 显式依赖与关键值（L2）

```yaml
    steps:
      - call: POST /orders
        with: { amount: 100 }
        as: order
      - call: POST /orders/{id}/pay
        with: { id: ${order.id} }
      - call: POST /refunds
        with: { orderId: ${order.id}, reason: "质量问题" }
        as: refund
        expect:
          - $.state == "REFUND_PENDING"
          - ${refund.amount} == ${order.amount}
          - db: refund[id=${refund.id}].status == "PENDING"
```

### 18.3 负向场景

```yaml
  - name: 未支付订单不能退款
    steps:
      - call: POST /orders
        as: order
      - call: POST /refunds
        from: [order]
        expect: { status: 409, $.code == "ORDER_NOT_PAID" }
```

### 18.4 异步结果：固定等待或授权轮询（L3）

```yaml
      - call: POST /exports
        expect: { status: 202, $.id exists }
        as: job
      - call: GET /exports/{id}
        with: { id: ${job.id} }
        wait: 10s                       # 固定等待后只查询一次
        expect: $.state == "DONE"
```

若使用者已在 `GET /exports/{id}` 的知识卡中授权轮询（例如每 2 s、最多 30 次、超时 60 s），可改为：

```yaml
      - call: GET /exports/{id}
        with: { id: ${job.id} }
        poll: true                      # 使用授权参数；只能等于或严于授权
        expect: $.state == "DONE"
```

### 18.5 使用函数

```yaml
      - call: POST /payments
        with:
          orderId: ${order.id}
          requestNo: ${fn.uuid()}                                   # RANDOM，值记录到运行报告
          expireAt: ${fn.timeShift("yyyy-MM-dd HH:mm:ss", "PT30M")} # CLOCK
        expect:
          - $.digest == ${fn.digest("SHA-256", ${order.id})}        # 预期值只能用 PURE 函数
```

签名、加密等调用约定要求的函数通常由平台按规则自动加入，使用者不必手写。

### 18.6 用户扩展示意（Java）

```java
package com.acme.octopus.functions.v1;   // 包名包含 .functions.（JMeter 规范）与版本标识

@OctopusTool(
    name = "acme.sign", version = "1.0.0",
    summary = "按 ACME 网关规则计算请求签名",
    description = "对请求体与 timestamp 按字典序拼接后计算 HMAC-SHA256，输出小写十六进制。",
    whenToUse = "调用 ACME 网关下需要 X-Sign 请求头的接口",
    whenNotToUse = "非 ACME 网关接口；回应验签",
    determinism = Determinism.PURE, stages = { Stage.REQUEST_TRANSFORM })
@ToolParam(index = 0, name = "body", type = "string", required = true, description = "最终发送的请求体 JSON")
@ToolParam(index = 1, name = "timestamp", type = "integer", required = true, description = "毫秒时间戳，须与请求头一致")
@ToolParam(index = 2, name = "secret", type = "string", required = true, sensitive = true, description = "签名密钥")
@ToolOutput(type = "string", format = "hex-64", description = "X-Sign 请求头的值")
@ToolExample(args = {"{\"a\":1}", "1700000000000", "<test-secret>"}, output = "3f2a…", description = "最小请求体")
@ToolExample(args = {"{}", "1700000000000", "<test-secret>"}, output = "9b0c…", description = "空请求体")
@ToolError(code = "SIGN_BODY_INVALID", description = "body 不是合法 JSON")
public class AcmeSign extends OctopusFunction {       // SDK 基类，继承自 AbstractFunction
    @Override protected Object compute(Args args) { /* 只依赖参数 */ }
}
```

上传后，平台自动识别为 `acme.sign@1.0.0`，生成文档页与 LLM 工具定义，通过自动校验、安全扫描与隔离测试后由上传者直接发布。

| DSL 声明 | 现有模型 |
|---|---|
| 场景 | Flow 的一个 TestPoint 及其 ordered steps 前缀 |

| `as` | FlowNode.outputs（解包后的业务主体） |
| 精确断言 / 回应类自然语言验证 | TestPoint.assertions（STATUS_EQUALS / JSON_* / SCHEMA_CONFORMS） |

| `cleanup` | Flow.cleanup |
| `role` / 推导角色 | FlowNode.role（新增） |
